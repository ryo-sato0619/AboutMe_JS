2. コンポーネント詳細
2.1. 監査ログ取得元
2.1.1. Microsoft Purview 監査ログ
取得方法:

推奨: Microsoft Graph Security API (/security/auditLogs/query) を利用。

件数制限対応: API応答に含まれる nextLink プロパティを利用したページネーションを実装し、指定された期間の全てのログを網羅的に取得します。Logic Apps の Until コントロールを使用して、nextLink がなくなるまでAPI呼び出しを繰り返します。

必要なAPIパーミッション: AuditLog.Read.All (Microsoft Graph Security API の場合)

2.1.2. Intune 監査ログ
取得方法:

推奨: Microsoft Graph API (/deviceManagement/auditEvents) を利用。

件数制限対応: Purview と同様に、API応答に含まれる nextLink プロパティを利用したページネーションを実装し、全てのログを網羅的に取得します。

必要なAPIパーミッション: DeviceManagementApps.Read.All, DeviceManagementConfiguration.Read.All, DeviceManagementManagedDevices.Read.All など、取得したいログの種類に応じた適切なパーミッション。

2.2. Logic Apps
監査ログの取得、加工（CSV変換）、格納、および通知を自動化するワークフローを設計します。

2.2.1. トリガー
種類: Recurrence (繰り返し)

設定:

Frequency: Day

Interval: 1

At these hours: 20 (日本時間の午後8時)

At these minutes: 0

Time zone: (UTC+09:00) Osaka, Sapporo, Tokyo (日本標準時)

2.2.2. 認証
推奨: マネージドID (Managed Identity) を使用。

種類: システム割り当てマネージドID

設定: Logic App リソースの「ID」ブレードで「システム割り当て済み」を「オン」に設定。

必要なロール割り当て:

Azure Blob Storage: Storage Blob データ共同作成者 または Storage Blob データ所有者 (コンテナーへの書き込み権限)。

Microsoft Graph API: Azure AD アプリケーション登録を作成し、必要なAPIパーミッションを付与。Logic App のマネージドIDに、そのアプリケーション登録のサービスプリンシパルに対する適切なロール (例: アプリケーション所有者) を付与するか、Graph API 呼び出し時にマネージドIDで直接認証できるコネクタ/カスタムコネクタを使用。

マネージドIDが不可の場合の考慮:

個人に紐づく認証情報を使用する際は、専用のサービスアカウントやグループアカウントの利用を検討し、特定の個人への依存を減らします。

認証情報の定期的な棚卸しと更新プロセスを確立し、異動や退職に備えます。

2.2.3. 監査ログ取得アクション
アクション: HTTP アクション (Microsoft Graph Security API 呼び出し用)

設定例 (Purview の場合):

Method: POST (Graph Security APIの auditLogs/query はPOSTを使用)

URI: https://graph.microsoft.com/v1.0/security/auditLogs/query

Headers: Content-Type: application/json

Body: 取得したいログの条件を指定します。例えば、特定の日付範囲やオペレーションタイプなど。

JSON

{
  "query": "Service=Microsoft365ComplianceAudit&Operations=FileAccessed",
  "startTime": "@{formatDateTime(addDays(utcNow(), -1), 'yyyy-MM-ddT00:00:00Z')}",
  "endTime": "@{formatDateTime(utcNow(), 'yyyy-MM-ddT00:00:00Z')}",
  "limit": 50000
}
startTime と endTime は、前日分のログを取得する Logic Apps の実行日時に応じて動的に生成します。

limit は一度に取得する最大件数を指定します。

Authentication: Managed Identity

Audience: https://graph.microsoft.com

ページネーション処理:

HTTP アクションの後に Until (〜まで繰り返す) コントロールを配置します。

Until ループの条件は、API応答の body('HTTP_アクション名')['@odata.nextLink'] が空ではない間、と設定します。

ループ内で HTTP アクションを繰り返し呼び出し、nextLink のURLを使用します。

取得した各ページのログデータを変数に追記し、全てのログを結合します。

エラー処理:

HTTP アクションの応答ステータスコードを確認し、エラー (例: 4xx, 5xx) の場合は後続の処理をスキップし、エラー通知フローに分岐させます。

2.2.4. データ加工（CSV変換）
アクション: Data Operations - Parse JSON (取得したログデータをJSONオブジェクトに変換)

アクション: Data Operations - Create CSV table

Create CSV table アクションは、JSON配列を入力として受け取り、CSV形式の文字列を生成します。

ネストされたJSON構造や複雑な変換が必要な場合は、Azure Function を利用することを検討します。

Azure Function (Python/C#など) でJSONデータを詳細にパースし、CSV形式に整形するロジックを実装します。

Logic Apps から Azure Functions コネクタを介してこのFunctionを呼び出し、JSONデータを渡し、CSVデータを受け取ります。

2.2.5. Azure Blob Storage への格納アクション
アクション: Azure Blob Storage - Create blob (V2)

設定:

Storage account name: (対象のストレージアカウント名)

Folder path: (コンテナー名)/[サービス名]/[年]/[月]/[日]

例: purview-audit-logs/@{formatDateTime(utcNow(), 'yyyy')}/@{formatDateTime(utcNow(), 'MM')}/@{formatDateTime(utcNow(), 'dd')}

Blob name: [サービス名]_[YYYYMMDD]_[HHMMSS].[拡張子]

例: purview_@{formatDateTime(utcNow(), 'yyyyMMdd_HHmmss')}.csv

Blob content: (CSV変換後のデータ)

Blob type: Block

Access tier: Hot

2.2.6. 通知（完了/エラー）
「スコープ」コントロールの配置:

監査ログ取得からBlob Storageへの格納までの一連のアクションを「スコープ」コントロールで囲みます。

スコープ名: Log_Collection_and_Storage_Scope など、分かりやすい名前にします。

成功時の完了通知:

スコープの後に「条件 (Condition)」コントロールを追加します。

条件式: @{equals(outputs('Log_Collection_and_Storage_Scope').status, 'Succeeded')}

「はい」の場合の処理:

アクション: Office 365 Outlook - Send an email (V2) または SendGrid - Send Email

To: (所定のメーリングリストのアドレス)

Subject: [完了] Logic App 監査ログ取得完了 - @{workflow().name}

Body: 処理が正常に完了した旨、Logic App の実行ID、完了日時、および格納されたログの概要（例: 格納されたファイル数、合計サイズなど、可能な範囲で）を含めます。

失敗時のエラー通知:

スコープの後に別の「条件 (Condition)」コントロールを追加するか、または上記の「条件」コントロールの「いいえ」のパスでさらに条件分岐させます。

条件式: @{equals(outputs('Log_Collection_and_Storage_Scope').status, 'Failed')}

「はい」の場合の処理:

アクション: Office 365 Outlook - Send an email (V2) または SendGrid - Send Email

To: (所定のメーリングリストのアドレス)

Subject: [緊急] Logic App 監査ログ取得エラー発生 - @{workflow().name}

Body: 発生したエラーの種類、Logic App の実行ID、エラー発生日時、関連するログ取得元、およびエラーの詳細（@{json(result('Log_Collection_and_Storage_Scope'))} など）を含めます。

3. セキュリティ考慮事項
最小特権の原則: Logic Apps のマネージドIDに付与するロールは、必要な最小限の権限に制限します。

ネットワークセキュリティ:

ストレージアカウントへのアクセスを、Logic Apps がデプロイされているVNetからのアクセスに制限する (プライベートエンドポイントまたはサービスエンドポイント)。

Logic Apps のアウトバウンドIPアドレスを固定し、必要に応じてファイアウォールルールを設定。

シークレット管理: APIキーや接続文字列などのシークレットは、Logic Apps のコードに直接ハードコードせず、Azure Key Vault に格納し、Logic Apps から参照するようにします。

4. 監視とアラート
Azure Monitor Logs (Log Analytics Workspace):

Logic Apps の診断設定を有効にし、すべてのログをLog Analytics Workspaceに送信します。

Kusto Query Language (KQL) を使用して、以下のクエリで監視します。

Logic App 実行成功/失敗:

コード スニペット

AzureDiagnostics
| where ResourceProvider == "MICROSOFT.LOGIC"
| where Category == "WorkflowRuntime"
| where resource_workflowName_s == "YourLogicAppName" // Logic App 名を指定
| summarize RunCount = count() by status_s
特定のアクションの失敗:

コード スニペット

AzureDiagnostics
| where ResourceProvider == "MICROSOFT.LOGIC"
| where Category == "WorkflowRuntime"
| where resource_workflowName_s == "YourLogicAppName"
| where status_s == "Failed"
| mv-expand properties_action_s
| where properties_action_s.status == "Failed"
| project TimeGenerated, resource_workflowName_s, properties_action_s.actionName, properties_action_s.error
Azure Monitor アラート:

アラートルール: Log Analytics Workspace 上で、上記のKQLクエリを基にアラートルールを作成します。

条件: 例: 過去5分間に Logic App の実行失敗が1回以上発生した場合。

アクショングループ: メーリングリストへのメール通知を設定したアクショングループを割り当てます。

5. コスト最適化
ストレージコスト:

3年間の保存期間中、アクセス頻度が低下する過去のログに対しては、ライフサイクル管理ポリシーで Hot → Cool → Archive 層への段階的な移行を検討します。これにより、ストレージコストを大幅に削減できます。

例:

最終変更後 30日経過: Hot から Cool へ移行

最終変更後 90日経過: Cool から Archive へ移行

最終変更後 1095日経過: 削除

Logic Apps コスト:

実行回数とアクション数に基づいて課金されます。不要な実行や冗長なアクションがないか定期的に見直します。

6. デプロイと運用
デプロイ:

Infrastructure as Code (IaC): Azure Resource Manager (ARM) テンプレート、Bicep、または Terraform を使用して、Logic Apps、ストレージアカウント、ライフサイクル管理ポリシー、監視設定などをコードとしてデプロイすることを推奨します。これにより、再現性と一貫性が確保されます。

運用:

定期的な監視: Azure Monitor を活用し、Logic Apps の実行状況、エラー、ストレージの使用状況などを定期的に監視します。

ログの確認: 必要に応じて、Azure Portal の Blob Storage または Azure Storage Explorer を使用して、格納されたログの確認を行います。

ライフサイクルポリシーの確認: ポリシーが意図通りに動作しているか、定期的に確認します。

API変更への対応: Microsoft Graph API や Purview API の変更があった場合、Logic Apps のワークフローを適宜更新する必要があります。

2.2.2. 認証
方式: マネージドID (Managed Identity)

設定: Logic App リソースの「ID」ブレードで、システム割り当て済みマネージドIDを有効にします。

2.2.3. 監査ログ取得とページネーションのワークフロー
変数初期化:

varLogData (Array型): 取得したログデータを一時的に格納する配列。

varNextLink (String型): ページネーションのための nextLink URLを格納。

ログ取得 (Purview) - Until ループ:

コントロール: Until (〜まで繰り返す)

条件: varNextLink が空ではない (@not(equals(variables('varNextLink'), '')))

アクション（ループ内）:

HTTPアクション: POST メソッドで Microsoft Graph Security API (/security/auditLogs/query) を呼び出します。

リクエストボディ:

JSON

{
  "query": "Service=Microsoft365ComplianceAudit&Operations=FileAccessed",
  "startTime": "@{formatDateTime(addDays(utcNow(), -1), 'yyyy-MM-ddT00:00:00Z')}",
  "endTime": "@{formatDateTime(utcNow(), 'yyyy-MM-ddT00:00:00Z')}",
  "limit": 50000
}
初回は固定の開始・終了日時、2回目以降はnextLinkを使用します。

応答処理:

Parse JSON アクションで応答ボディをパース。

nextLink が存在する場合、varNextLink 変数を更新します。

Compose アクションでログデータを抽出・整形し、varLogData 配列変数に追加します。

Intune ログも同様にページネーションで取得し、varLogData に結合します。

2.2.4. データ加工 (CSV変換)
CSVヘッダー定義:

ログデータから抽出するフィールドを決定し、CSVのヘッダーを定義します。

例: Timestamp,UserId,Operation,ResultStatus

JSONからCSVへの変換:

Data Operations - Create CSV tableアクション:

From: varLogData

Headers: Custom を選択し、定義したヘッダーを配列で入力します。

詳細: シンプルなJSON構造の場合は有効です。

Azure Function (推奨):

言語: Python/C#

ロジック: varLogData をJSON配列として受け取り、CSVライブラリを使用してCSV文字列に変換します。ネストされたJSONをフラット化し、ヘッダーに合うようにフィールドをマッピングするロジックを実装します。

3. セキュリティ考慮事項
Key Vault:

rg-audit-log-prod-central リソースグループ内にAzure Key Vaultをデプロイします。

APIキーや接続文字列などのシークレットはKey Vaultに格納し、Logic Apps から参照するように構成します。

Logic Apps のマネージドIDに、Key Vaultの「シークレットの取得」権限を付与します。

ネットワーク:

ストレージアカウントで「選択された仮想ネットワークとIPアドレスから有効」なアクセスを許可する設定を行い、Logic AppsのアウトバウンドIPアドレスを許可リストに追加します。

4. 監視とアラート
Logic Apps 診断設定:

Logic App の診断設定を有効化し、WorkflowRuntime カテゴリのログを Log Analytics Workspace に送信するように構成します。

Azure Monitor アラート:

アラートルール: Logic App の実行ログをクエリし、status_s == "Failed" の場合にアラートを発生させます。

アクショングループ: 担当者やメーリングリスト宛てのメール通知をアクショングループとして定義し、アラートルールに紐づけます。

5. 運用と保守
デプロイメント:

ARMテンプレートまたはBicepファイルを作成し、リソースグループ、Logic Apps、ストレージアカウント、およびRBACロール割り当てをコードとしてデプロイします。

これにより、開発環境 (rg-audit-log-dev-central) と本番環境を簡単に同期・管理できます。

定期的なレビュー:

ログ量やAPI仕様の変更に備え、年に一度など定期的に本設計を見直します。
